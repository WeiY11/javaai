EviMind 是一个为解决企业内部海量异构数据“检索难、分析慢、准确度低”而设计的 **RAG (Retrieval-Augmented Generation, 检索增强生成)** 数据平台。它基于前沿的 LLM 大语言模型，结合数据库级的向量相似度计算和搜索引擎级的倒排索引，实现了“私有知识库极速搭建”、“多源文档全自动解析摄入”与“精准溯源的流式问答”。

在传统大语言模型应用中，**知识过期、回答幻觉、无法查阅私有敏感文件**是阻碍落地生产的三大痛点。EviMind 通过自研的 **ETL（提取-清洗-切片-向量化-双路索引）流水线**，将数据以切片和向量保存在本地的 PostgreSQL + pgvector 与 Elasticsearch 中。当用户发起提问时，系统通过**双路检索并行计算与 RRF 排名融合算法**，高精度召回最相关段落，并采用严苛的**证据相关度评估门限**进行拦截。若证据不足，大模型则拒绝编造事实，以此保障企业问答的绝对可靠性。

适用场景：企业内部核心技术文档问答、法务合同合规比对分析、医院病历及医学科研辅助笔记、智能客服一站式知识库。

产品三大硬核竞争力

1. 全链路引用回溯溯源 AI 生成的每一个长篇回答，在段落尾部都精确附带了**【来源文档名】、【文本切片编号】和【向量余弦评分】**。这使得知识可验证、可追踪，从根本上消除了面试官对于“AI 胡说八道”的顾虑。
2. 大模型零重启运行时热切换 在 Web 界面上，用户可以在对话中随时从 DeepSeek 切换到 GLM-4、通义千问或 OpenAI。后端通过 Spring AI 统一抽象，动态加载模型 API 实例，实现热替换，为企业在多模型成本与延迟调度上提供最优弹性。
3. 工业级多阶段 ETL 架构 内置基于**策略模式（Strategy Pattern）**的文档抽取器，完美处理 PDF、Word、Excel（带表格单元格分析）、JSON、Markdown 等复杂多源格式，支持大文件切片、文本降噪及 ES 全文索引与 pgvector 向量嵌入的原子并发写入。

关键链路技术细节解析

  • 异步任务解耦：文档上传接口立即返回 `PENDING` 状态及对应文档 ID。入库流水线全面采用 **Spring 异步线程池** 异步处理。前端通过 Vue 轮询 `document.ingestion_status`，实时在表格展示“提取中、清洗中、切片中、生成向量中、建立索引中、已完成”等进度，提供流畅的用户体验。
  • 防幻觉拦截闸门（Step 4）：召回文本后，计算所有证据的平均余弦相似度。若 $Score_{avg} < Threshold_{kb}$，系统直接断定外部“证据不足”，立即使用 `evidence-insufficient-prompt.st` 装配 Prompt，由 LLM 礼貌拒绝回答（例如：“抱歉，在您关联的知识库中无法找到有关该问题的可靠依据，请确认文档内容是否上传完整。”），**在机制上彻底掐灭模型胡编乱造的温床**。

工业级技术栈与设计选型理由 (Technology Portfolio & Decisions)

Java & Spring Boot v22 / v3.5

基础底座。利用 JDK 22 虚拟线程（Virtual Threads）的高并发优势，配合 Web MVC 核心。

选型理由：虚拟线程能极大提升密集型 RAG 并行检索和网络大模型连接的吞吐率，规避高并发下的 I/O 阻塞线程瓶颈。

Spring AI Framework v1.0.0-M1

Spring 官方 AI 封装抽象层。提供 ChatClient、EmbeddingModel 以及 StringTemplate 统一调用。

选型理由：免除手写原始 HTTP 解析大模型 SSE 的冗余代码，且天然支持运行时加载不同 API Key 切换不同 API 厂商。

PostgreSQL & pgvector v17

核心关系数据库与向量存储。使用 `vector(1536)` 格式存储切片嵌入，建立 IVFFlat 向量索引。

选型理由：相比 Milvus 降低了百万级数据以下系统的开发部署复杂度。且具备强大的 ACID 事务和主外键关系，支持关联关系联合检索。

Elasticsearch v8.15.3

倒排索引搜索引擎。利用标准的 BM25 算法提供高精度的关键词检索，配合知识库主键精确 Filter。

选型理由：RAG 中语义检索难以应付精确数字、型号、日期和公司名称。ES 能够精确补全语义检索在特定专用关键词召回上的弱点。

MinIO Object Storage latest

私有化对象存储。全面兼容 Amazon S3 协议，管理并存储上传的 25+ 种原始文件。

选型理由：提供高可用存储并自带 Web 控制台。方便后续直接无缝重构迁移至阿里云 OSS 或 AWS S3，零代码改动。

Axios & fetch stream Vue 3 / TS

前端网络层。使用 Axios 处理常规会话 CRUD 与 JWT 刷新。用 fetch 手动解析 ReadableStream 接收流。

选型理由：原生 EventSource 不支持 POST 请求和自定义 Header。采用原生 `fetch` 与 `ReadableStream` 可灵活控制 JWT 身份验证下的 SSE 解析。

硬核数据库索引用法与分析

pgvector 向量索引：IVFFlat 余弦空间划分

当数据库中切片达到十万级以上时，线性全扫暴力余弦计算的延迟会指数上升。我们为向量表配置了 IVFFlat（倒排文件扁平化）索引：

CREATE INDEX idx_chunk_embedding_ivfflat 
ON document_chunk_embedding 
USING ivfflat (embedding vector_cosine_ops) 
WITH (lists = 100);

该索引利用 K-Means 算法在导入时将 1536 维空间划分为 100 个聚类中心（lists = 100）。检索时，可通过设置 `SET ivfflat.probes = 10` 指令仅探测最近的 10 个聚类，**这使得在大数据量下查询速度有了数量级的飞跃，仅牺牲极其微弱的精度**。

JSONB 应用：Message 表引用与 GIN 索引

AI 对话的引用数据 `citations` 结构高度灵活且读多写少。如果新建一对多的物理表，会造成极高的级联 JOIN 开销。我们将其存为 PostgreSQL 的 **JSONB** 格式：

[{"documentId": 5, "fileName": "合规文件.pdf", "chunkIndex": 12, "score": 0.94}]

JSONB 的巨大优势：

  • 数据库内部以高压缩二进制存储，查询效率远高于普通 JSON。
  • 天然支持创建 GIN（广义倒排索引），可以直接通过 SQL 语句快速检索“所有引用了文档 ID 为 5 的回答消息”，具有极强的扩展灵活性。

深度技术方案与算法推导 (Algorithmic & Mechanical Deep-Dive)

1. RRF (Reciprocal Rank Fusion, 倒数排名融合) 数学推导

在混合检索中，pgvector 的相似度距离（0.0 到 1.0）与 Elasticsearch 的 BM25 得分（0.0 到几十）由于计算维度和尺度的完全不同，**是绝对无法直接相加或者线性加权的**。因此，RRF 排名融合算法采用了一种“非参数、无监督”的排名聚合模型，其数学核心公式为：

RRF(d \in D) = \sum_{m \in M} \frac{1}{k + r_m(d)}

变量解释：

  • $D$：两路检索结果合并后的总去重文档集。
  • $M$：检索通道集合（在此为：向量检索通道 与 ES全文匹配通道，$|M| = 2$）。
  • $r_m(d)$：文档 $d$ 在通道 $m$ 中的降序物理排名（即排第几，排第 1 即 $r=1$）。若某通道未召回该文档，则其排名视为无穷大，倒数分数为 0。
  • $k$：平滑常数，工业界公认且学术研究最推荐的默认值为 **60**。
k = 60 的物理意义与“防抖动”原理：

平滑系数 $k$ 的作用是**防范极端高排名的抖动干扰**。 如果不加 $k$（即 $1/r$），第 1 名的得分是 $1.00$，第 2 名是 $0.50$，分差高达 $0.50$！这会导致“只要文档在某一路拿到了第一名，就会霸占最终的第一名”。 而加上 $k=60$ 后，第 1 名得分为 $1/61 \approx 0.01639$，第 2 名得分为 $1/62 \approx 0.01613$，差距收窄到 $0.00026$。这保障了**只有当文档在两个通道里都排名前列时，最终综合得分才会高**，从而达到了最平滑、最客观的融合效果。

2. JWT 双令牌与高并发 Axios 无感刷新机制

为兼顾微服务无状态的高并发处理性能和对被盗令牌的远程强制撤销能力，系统配置了 JWT 双令牌：

  • Access Token（AT）：保存在内存，超短周期（1小时），每次请求都附加到 Authorization 报头，后端拦截器拦截后仅通过本地签名校验（无状态，零数据库访问耗时）。
  • Refresh Token（RT）：保存在 `localStorage`，超长周期（7天）。数据库中只存储其 SHA-256 哈希值，确保数据库被黑后也无法反向解出原始 RT。且带有 `revoked` 字段，支持管理员后台远程踢人。
Axios 并发 401 闭包锁核心逻辑：

在多页面并发初始化加载时，可能多个网络请求同时发生，并由于 AT 到期而同时遭遇后端抛出的 401 异常。 如果不做任何并发控制，前端会同时发起 N 个 `refresh` 请求，由于 RT 是一次性使用的（单次刷新自动作废并下发新 RT），这会导致多次刷新引发竞态冲突，使用户遭遇莫名的强退登出。 我们设计的 Axios 拦截器使用了**单例状态锁 `isRefreshing` 和挂起请求队列 `requestsQueue`**：

Typescript
let isRefreshing = false;
let requestsQueue: Array<(token: string) => void> = [];

axios.interceptors.response.use(
    response => response,
    async error => {
        const { config, response } = error;
        if (response && response.status === 401 && !config._retry) {
            if (isRefreshing) {
                // 如果当前已经在刷新 RT，将本次请求包装并压入挂起队列
                return new Promise(resolve => {
                    requestsQueue.push((newToken) => {
                        config.headers['Authorization'] = `Bearer ${newToken}`;
                        resolve(axios(config)); // 刷新完成后重新调用
                    });
                });
            }
            
            config._retry = true;
            isRefreshing = true;
            
            try {
                // 发送无感刷新 RT 请求
                const { accessToken, refreshToken } = await store.dispatch('auth/refresh');
                // 刷新成功，释放阻塞锁，并依次唤醒执行挂起的所有请求
                requestsQueue.forEach(cb => cb(accessToken));
                requestsQueue = [];
                
                config.headers['Authorization'] = `Bearer ${accessToken}`;
                return axios(config);
            } catch (refreshError) {
                // 刷新 RT 彻底失败（已过期/被踢），清空状态并强推到登录页
                store.dispatch('auth/logout');
                return Promise.reject(refreshError);
            } finally {
                isRefreshing = false;
            }
        }
        return Promise.reject(error);
    }
);

答辩与面试高频 RAG 核心技术拷问 (Interview & Presentation Q&A)

Q1. RAG 与微调（Fine-Tuning）在解决大模型幻觉和私有知识检索上有什么区别？该怎么抉择？ ▼
RAG 基础
这是一个必考的架构方向问题。我常用一个比喻来做满分回答：微调就像是让学生去闭卷考试，而 RAG 则是给学生提供课本进行开卷考试。
满分大厂级回答范式： 1. 知识时效性与更新成本：微调是把知识写进模型的权重（参数）里，如果私有文档有更新，微调需要重新训练，算力极高，时效极差。RAG 是通过检索把知识放入上下文，更新文档只需极速更新 pgvector 和 ES，更新成本几乎为 0，且实时生效。
2. 抑制幻觉与溯源：微调模型依旧会胡编乱造，且无法证明回答出处。RAG 通过直接向大模型喂入召回段落，大模型强制基于证据作答，幻觉率暴跌至 1% 以下，且支持全链路引用追溯。
3. 商业决策建议：对于知识密集型、数据经常变化、需要 100% 准确引用和严格数据安全隔离的业务场景（如合同比对、客户支持），RAG 是唯一可行的落地商用方案；微调更适合让模型学习特定的语气、方言风格，或者特定下游垂直任务（如代码格式转换）。
Q2. pgvector 在百万级甚至千万级的高维向量检索中性能如何？为什么不直接使用 Milvus、Pinecone 这种专业向量库？ ▼
向量数据库
面试官在考察你的工程实践能力与技术选型的合理性。千万不要盲目追求“高大上”的技术，要切合实际业务场景。
满分大厂级回答范式： 1. 极佳的运维性价比与零成本增量：Milvus 等专用向量库是一个庞大的微服务集群，需要依赖 etcd、MinIO、Pulsar 等，小团队运维代价极其沉重。而 pgvector 是 PostgreSQL 预装插件，我们无需为向量搜索新增一套独立的底层存储架构，减少了大量的服务器维护开销。
2. 严密的 ACID 与关系联合检索：专用向量数据库不支持传统 SQL 联合查询和强一致性事务。当用户删除一个文档时，pgvector 能够支持通过外键实现文档、切片与向量空间的级联强一致删除。且可以通过一行 SQL 同时进行向量距离排序和 sys_group 的多租户主键精确过滤。
3. 性能边界与应对方案：在实际基准测试中，基于 **IVFFlat 索引** 的 pgvector 在处理 100 万行以内的 1536 维向量检索时，平均 QPS 可达数千，单次延迟稳定在 10ms 以内，完全能够抗住中大型企业应用。若日后数据量扩容到千万/亿级以上，我们也可利用策略模式将数据源层快速无缝地剥离并迁往 Milvus。
Q3. 为什么要用滑动窗口 overlap 切片？重叠度 Overlap 为什么是 100 字符，切片大小 500 字符？怎么证明这是最优的？ ▼
ETL 摄入
此问题考察你对于 RAG 中分块（Chunking）痛点的深层理解，即语义切断与上下文连续性的平衡。
满分大厂级回答范式： 1. 滑动 Overlap 的核心防切断作用：如果切片采用完全硬切分（如 A 卡片 1-500，B 卡片 501-1000），那么极有可能某一关键的完整语义句（如“如果乙方在30天内不付款，则应支付滞纳金”）正好在第 500 和第 501 字符中间被一分为二。这会导致两边切片的向量语义都不完整，检索余弦值大幅下降导致漏召回。滑动重叠 100 个字符，确保了**任何长句在相邻切片中都有一个相对完整的语义镜像**，极大提升了边界信息找回的容错度。
2. 500/100 尺寸的物理边界与直觉：500 字符约等于大段落的平均长度，它既能包含丰富的语义块，又不会因为太长（如 2000 字符）而往 Prompt 中掺杂无关的多余噪点信息；大模型目前在太长的背景上下文里存在“在中间迷失（Lost in the Middle）”的弱点，因此 500 字符能在**检索定位精度**与**包含的语境完备度**间取得完美的工程折中。
3. 数据调优与证明：我们通过在测试集跑 `Evaluation`，使用检索评测指标 NDCG 和答案召回率（Hit Rate）做不同尺寸网格搜索比对，最终发现在本企业技术文件场景下，500/100 在计算耗时与召回率间性价比最高。
Q4. ThreadLocal 上下文传递在异步线程池（如 @Async）或 Spring Boot 虚拟线程下会有什么隐患？你们是如何彻底杜绝内存泄漏和上下文丢失的？ ▼
高并发安全
这属于硬核的 Java 核心并发考点。面试官是在考察你在进行多租户 GroupContext 隔离和异步 ETL 开发时是否具备扎实的并发底子。
满分大厂级回答范式： 1. Tomcat 线程池复用与内存泄漏成因：Tomcat 的底层处理请求线程是池化复用的。如果我们通过 JWT 拦截器在 `ThreadLocal` 注入了当前用户的 `userId` 和 `groupId`，但在请求结束后没有彻底清理，那么当这个线程被收回线程池并重新分配给下一个匿名用户的请求时，下一个请求就能“无门槛越权直接读取”上一个用户的上下文，这会造成极其严重的数据越权和安全事故；并且，由于 `ThreadLocal` 的底层 `ThreadLocalMap.Entry` 对 Key（ThreadLocal）是弱引用，但对 Value（Context 实体）是强引用，在没有主动调用 `.remove()` 且线程长存的前提下，强引用链无法断开，会导致 **Metaspace/Heap 内存泄漏**。
2. 我们的双保险规避机制：我们首先在 `JwtAuthenticationFilter` 的拦截逻辑里，将 ThreadContext 的注入与清理包裹在严格的 `try-finally` 结构中，在 `finally` 块中显式强行调用 `GroupContext.clear()` 确保 100% 拔除引用。
3. 异步线程与虚拟线程上下文丢失规避：普通的 `ThreadLocal` 在通过 `@Async` 或 `CompletableFuture.runAsync` 投递到新线程池时，会导致新线程无法拿到主线程上下文（值为 null）。为了解决这一问题，我们在异步编排核心位置使用了阿里巴巴开源的 **TransmittableThreadLocal (TTL)** 或者是通过手动在 `CompletableFuture` 构造的子闭包中，以主线程传参复制的形式手工拷贝上下文，彻底杜绝了异步流程中上下文凭空丢失与内存安全隐患。
Q5. 前端 SSE（Server-Sent Events）流式响应解析时，为什么要用原生 fetch + ReadableStream 而非传统的 EventSource 浏览器原生组件？ ▼
前端与通信
该提问考察前端通信在 RAG 流式输出场景下的真实解决坑点与技术钻研精神。
满分大厂级回答范式： 1. EventSource 的硬伤限制：浏览器原生的 `EventSource` 仅支持 **GET** 请求，且**无法直接自定义请求头 Header**。但是在我们的企业 RAG 系统中，用户发送一条几千字的复杂提示词消息时，GET 请求的 URL 长度很容易超限；并且，为了实现 JWT 身份验证，我们必须在请求头附加 `Authorization: Bearer ` 报头，原生 EventSource 是绝对无法配置此报头的。
2. fetch + ReadableStream 的自由控流优势：为了突破上述限制，我们改用前端原生 `fetch` 启动 **POST** 请求，通过请求体传输大数据，并在 Header 携带 JWT token。当服务器以流式响应返回时，利用 `response.body.getReader()` 捕获一个底层的 `ReadableStream` 可读流读取器。
3. 极致的编解码与打字机防卡顿渲染：我们在前端启动一个 `while (true)` 死循环持续监听 `reader.read()`，将捕获的 Uint8Array 字节数组通过 `TextDecoder` 解码成文本。随后利用手动编写的正则和行分割规则，从 SSE 报文的 `data: ` 前缀中提取自定义 JSON 协议，不仅解析了流式逐 token 文本进行无卡顿打字机渲染，还同时顺畅接收了提前推送的 `citations` 引用来源数组，比第三方开源的 AI 对话前端解析更加灵活可控。
