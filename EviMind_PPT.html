Part 1. 为什么必须用 RAG？

大白话带你搞懂行业痛点

大模型的“幻觉”与企业数据的“孤岛”

痛点一：大模型会“胡说八道”

大模型（如 ChatGPT）就像一个读过无数书但不允许带书进考场的考生。当你问它企业内部机密问题时，它为了不交白卷，会凭印象“编造”假答案。

痛点二：传统搜索“不懂人话”

传统搜索（如 Elasticsearch 的 BM25）靠“关键字匹配”。你搜“降本增效”，文章里写的是“削减开支”，它就死活搜不出来，因为它不懂语义。

如何破局？

这就是 EviMind (基于 RAG 架构) 诞生的意义：把“闭卷考试”变成“开卷考试”。系统收到问题后，先去数据库里找出最相关的内部机密文档，然后把这些文档和问题一起发给大模型，让大模型“照着书念”，彻底消灭幻觉！

Part 2. 全栈技术架构选型大阅兵

为什么不用大杂烩，而要选这些顶级组件？

后端核心架构与组件生态

☕ 核心框架与 ORM

  • Java 21: 彻底拥抱虚拟线程 (Virtual Threads)，用极小的内存扛住高并发连接。
  • Spring Boot 3.5: 最新一代企业级容器底座。
  • MyBatis-Plus: 最懂中国程序员的 ORM。提供强大的 Lambda 条件构造器（LambdaQueryWrapper）和 MetaObjectHandler 自动字段填充。
  • Spring AI: 官方正统的 AI 大模型抽象层。一套 API 无缝切换 OpenAI / 智谱 / 通义千问。

🗄️ 数据库与中间件

  • PostgreSQL 16 + pgvector: EviMind 的心脏。这不仅是关系型数据库，它的 JSONB 能秒杀 MongoDB，而它的 pgvector 插件则是当今最主流的向量检索引擎（存放 1536 维数据）。
  • Elasticsearch 8.x: 提供 BM25 倒排索引支持，用于兜底“纯关键字精确匹配”。
  • MinIO: 开源的企业级对象存储，兼容 S3 协议，安全存储用户上传的几十兆原始 PDF。
  • Flyway: 数据库界的 Git。绝不用危险的 ddl-auto:update，严格靠 SQL 脚本迁移，防范删表跑路。

为什么要用这么“重”的架构？

你可能会说：“我用 Python 的 LangChain + SQLite，几十行代码也能跑通一个 RAG”。
但是在企业级生产环境中，你的系统需要：防越权漏洞、支撑万级用户并发、保证文档隔离、保存结构化的工具调用记录。Python 脚本就像是搭积木玩具，而 Java Spring 生态 + PostgreSQL/ES 的这套组合拳，则是真正的“钢筋混凝土摩天大楼”。这才是进大厂、干大项目的核心工业级标准。

前端架构选型与防线部署

💻 视图与状态流转

  • Vue 3 (Composition API): 摒弃 Options API，利用 <script setup> 带来的极简心智负担。
  • TypeScript: 强类型约束极其重要。因为 AI 会返回极其复杂的 JSON（比如工具调用格式），没有类型提示前端早就崩溃了。
  • Pinia: 取代 Vuex。它的响应式机制是“SSE 流式打字机效果”的底层功臣（对象被推入后，只需对 content 进行加法拼接，Vue 就会自动重绘）。
  • Vite 8: 抛弃笨重的 Webpack，利用浏览器原生 ES 模块机制，毫秒级冷启动。
  • Element Plus: 支撑了左侧弹窗、折叠面板等复杂的交互组件。

🛡️ 渲染引擎与安全防线

  • Markdown-It: 把 AI 返回的 Markdown 语法转成 HTML。
  • Highlight.js: 给大模型写的 Python/Java 代码加上漂亮的代码高亮。
  • DOMPurify (极其关键): AI 生成的 HTML 里可能包含恶意的 <script> 标签。DOMPurify 充当最后一道防线，在 HTML 渲染到页面前，把所有的投毒脚本彻底清洗干净，防止 XSS 跨站攻击。

前后端分离是如何通信的？

EviMind 的前端极其清爽。对于普通的增删改查，前端利用 Axios 发送带有 JWT 的 JSON 请求；而对于核心的聊天界面，前端利用原生浏览器的 fetch + ReadableStream 接收后端的 Server-Sent Events (SSE) 事件流。这就好像后端在用电报机“哒哒哒”地往前端逐字拍电报，前端一边收一边渲染！

Part 3. 数据库设计到底有多细节？

JSONB 与 向量索引的架构之美

为什么 message 表要大量使用 JSONB？

CREATE TABLE message (
    id BIGSERIAL PRIMARY KEY,
    content TEXT NOT NULL,
    citations JSONB,    -- 存储AI回答时引用的文献片段
    tool_calls JSONB    -- 存储大模型调用的工具记录
);

告别恐怖的“连表查询灾难”

在传统的系统设计中，一个对话可能包含 50 条消息，每条消息又可能引用了 5 个文献片段。如果用传统的关系型设计，你需要建一张中间表。每次打开聊天记录，数据库就要做庞大而复杂的 JOIN 连接操作，数据库会被拖垮。

PostgreSQL 的杀手锏：JSONB。
我们把引用文献的名字、得分、内容，直接打包成一个 JSON 数组存在 citations 中。读取一条消息时，它的引用数据瞬间就能一并被提取出来，完全没有连表开销！不仅如此，PG 还允许我们在 JSONB 字段上建立 GIN 倒排索引。

Elasticsearch 倒排索引的坑点避雷

"mappings": {
  "properties": {
    "content":       { "type": "text", "analyzer": "standard" },
    "knowledgeBaseId": { "type": "keyword" }, // ⚠️ 这里极度关键！
    "documentId":    { "type": "keyword" }
  }
}

为什么 ID 必须是 keyword 而不是 integer？

这是一个极其高频的面试坑点。
如果你把 ID 设为 integer，Elasticsearch 底层会为它构建 BKD Tree（多维范围树），这种结构是为 age > 18 这种“范围查询”优化的，但对于精确相等查询（ID == 5）反而很慢！
而 keyword 类型底层构建的是 倒排字典树。我们在做混合检索时，只需精准命中字典里的这一项，速度呈指数级提升。

文本切片 (Chunking) 的滑窗防断层算法

private String getOverlapText(String text, int overlapSize) {
    int targetStart = text.length() - overlapSize;
    // 分别向前和向后寻找最近的标点符号（如句号、感叹号、回车）
    int breakBefore = findPunctuationBackward(text, targetStart);
    int breakAfter = findPunctuationForward(text, targetStart);
    
    // 比较向前和向后哪个离目标截断点更近，就在那个标点之后截断
    int bestStart = (targetStart - breakBefore) <= (breakAfter - targetStart) ?
                    (breakBefore + 1) : (breakAfter + 1);
    
    return text.substring(bestStart).trim();
}

为什么要找标点符号截断？

如果用户规定每个切片 500 字，重叠 100 字。最粗暴的做法就是用 substring 生硬切断。但这会导致一句话可能刚说了一半被残忍切断，后续打成的向量也就成了垃圾。

这段源码展示了 EviMind 的语义级滑窗算法：找到硬截断点附近最近的一个句号，确保切片重叠部分是一整句完整的话，极大地保证了上下文语意的连贯性。

并发双路搜索与优雅降级

CompletableFuture<List<SearchResult>> semanticFuture = 
    CompletableFuture.supplyAsync(() -> pgVectorSearchService.search());

CompletableFuture<List<SearchResult>> keywordFuture = 
    CompletableFuture.supplyAsync(() -> elasticsearchSearchService.search());

把串行变为并行，压榨性能极限

PostgreSQL 向量查询和 ES 查询，要走两次不同的网络请求。我们使用了 CompletableFuture 开启异步并发，总耗时直接降到了 MAX(T1, T2)。

高可用降级（Try-Catch）： 如果 ES 所在的那台服务器挂了，系统会抛出 TimeoutException。我们在 Catch 块里直接给一个空列表，让系统依靠剩下的一路向量查询继续走下去，绝不给用户返回 500 错误！

Agentic RAG、权限隔离、JWT防伪与防内存泄漏

RAG 的终极形态：大模型函数调用 (Agentic RAG)

@Bean
@Description("在知识库中检索相关文档。当提问涉及知识库时，调用此工具。")
public Function<KbSearchRequest, KbSearchResponse> kbSearch() {
    return request -> {
        // 调用底层双路混合检索
        List<SearchResult> results = hybridSearchService.search(
                request.query(), request.knowledgeBaseId(), topK);
        // ... 返回格式化后的字符串
        return new KbSearchResponse(formatResults(results), null);
    };
}

从“死板执行”到“智能中枢”的飞跃

传统的 Naive RAG 是极其死板的：不管用户问什么，系统都会去查数据库。这不仅浪费资源，还会干扰大模型的闲聊。

EviMind 利用了最新的 Function Calling 技术，进化到了 Agentic RAG。我们只需通过 @Description 注释告诉大模型这把工具的存在。接下来，是否要进行数据库搜索，完全由大模型自己决定！ 这是未来 AI 系统的终极形态。

企业级多租户：绝对不容商量的鉴权隔离

public KnowledgeBase update(KnowledgeBase kb) {
    if (!isOwner(kb.getId())) {
        throw new SecurityException("只有 OWNER 才能更新");
    }
}

public boolean isOwner(Long kbId) {
    Long userId = GroupContext.getUserId(); // 从 ThreadLocal 拿
    return kbMemberMapper.selectCount(
        new LambdaQueryWrapper<KbMember>()
            .eq(KbMember::getKnowledgeBaseId, kbId)
            .eq(KbMember::getUserId, userId)
    ) > 0;
}

防越权 (BOLA 漏洞) 是架构的底线

如果黑客抓包把 kbId 改成了竞争对手公司的知识库 ID 企图进行破坏。

在 KnowledgeBaseService 中，所有写操作的第一行，永远是 !isOwner() 判断！系统绝对不信任前端传来的用户身份，而是严格从经过 JWT 解码的 ThreadLocal 中提取身份，并在数据库关系表中进行强校验。查不到？直接踢飞！

源码：JWT 双令牌签发防伪造

private SecretKey getSigningKey() {
    return Keys.hmacShaKeyFor(jwtConfig.getSecret().getBytes(UTF_8));
}

public String generateAccessToken(Long userId, String username, String role) {
    return Jwts.builder()
            .subject(userId.toString())
            .claim("role", role)      // 暴露的业务数据
            .signWith(getSigningKey()) // ★ 无法伪造的防线！
            .compact();
}

无状态架构的杀手锏：数字签名

JWT 的神奇之处在于：后端验证用户的请求时，不需要去查数据库验证他到底是谁！
我们在发令牌时使用了只有服务器端自己知道的极高强度 SecretKey，对数据进行了 HMAC-SHA256 加密签名。黑客改动了哪怕一个字母的 Payload，算出来的哈希值立刻对不上，直接报废踢出。这就是密码学带来的极致信任。

ThreadLocal 的天使与魔鬼

protected void doFilterInternal(...) {
    GroupContext.setContext(userId, groupId, role);
    try {
        filterChain.doFilter(request, response); // 放行请求
    } finally {
        // ⚠️ 极其致命的清理！
        GroupContext.clear();
    }
}

为什么 finally 绝对不能漏？

Tomcat 使用的是线程池技术。这意味着一个 HTTP 请求处理完后，处理它的那个线程不会被销毁。如果你不在 finally 里把包含凭证的 ThreadLocal 清空，下一个完全不同的用户不小心复用了这个线程，他就能直接读取到上一个用户的身份凭证，导致极其严重的越权访问漏洞！

JWT 无感刷新：防踩踏并发死锁

let isRefreshing = false; // 全局锁
let requestsQueue = [];   // 被挂起的请求回调队列

axios.interceptors.response.use(res => res, async (error) => {
    if (error.response.status === 401 && isRefreshing) {
        // 别人在刷新，把自己挂起到队列里，返回暂未兑现的 Promise
        return new Promise(resolve => requestsQueue.push(newToken => resolve(axios(...))));
    }
    
    // 我是第一个发现 401 的，我来刷新
    isRefreshing = true;
    const newToken = await doRefresh(); 
    requestsQueue.forEach(cb => cb(newToken)); // 唤醒被挂起的兄弟
    requestsQueue = []; isRefreshing = false;
});

什么是“刷新踩踏”？

通过引入 isRefreshing 这个**全局闭包锁**，在多个请求同时遇到 401 的瞬间，只有第一个请求负责去换新钥匙，其余请求全被推入内存数组中“休眠等待”。等钥匙一到手，批量分发唤醒重试，完美实现“并发无感”操作！

Part 8. 结语

真正的企业级开发，难在哪里？

看完了这么多行代码与架构图，你会发现：写出一个“能运行”的 RAG 也就是几百行 Python 脚本调个 API 的事。但要写出一个“能经受企业环境考验”的系统，却难如登天。

真正的核心竞争力，就在于这套“全栈工业级架构选型”中：
📌 你的架构是否先进？（Agentic RAG 函数调用自动调度）
📌 你是否防住了极其隐蔽的越权漏洞？（KnowledgeBaseService.isOwner 强拦截）
📌 你是否考虑了网络超时的优雅降级？（CompletableFuture 并发编程）
📌 你的数据库能承受高频的引用列表连表查询吗？（PostgreSQL JSONB 逆天性能）
📌 你的多租户上下文鉴权会不会导致内存泄漏？（ThreadLocal finally 必须 clear）

这些藏在冰山下的严苛细节，才是 EviMind 这套源码真正的价值所在。
