# 需求规格文档 - 强化文件分析能力

## 文档信息
| 项目 | 内容 |
|------|------|
| 特性名称 | enhanced-file-analysis |
| 版本 | 1.0 |
| 创建日期 | 2025-04-25 |
| 状态 | 草稿 |

## 1. 概述
### 1.1 特性描述
本特性旨在强化现有 AI 对话与实验数据管理平台的文件分析能力，从三个维度进行增强：扩展支持的文件格式（新增 PDF 内容提取、Excel 电子表格解析、Word 文档解析）、增加批量分析功能（支持一次选择多个文件进行 AI 分析）、以及增加分析结果导出功能（支持将 AI 分析结果导出为 Markdown 或 PDF 报告）。

### 1.2 范围
#### 1.2.1 包含范围
- PDF 文件内容提取与文本解析，使 PDF 文件可被 AI 分析
- Excel（.xlsx/.xls）文件内容解析，提取工作表结构与数据
- Word（.docx/.doc）文件内容解析，提取文档文本内容
- 批量文件选择与批量 AI 分析功能
- 批量分析进度跟踪与状态展示
- 单文件分析结果的结构化存储
- 分析结果导出为 Markdown 格式报告
- 分析结果导出为 PDF 格式报告
- 文件格式分类体系的扩展（新增 pdf-extractable、excel、word 类别）

#### 1.2.2 排除范围
- 文件编辑与修改功能
- 文件格式转换功能（如 Word 转 PDF）
- AI 模型训练或微调
- 用户认证与权限管理
- 分析结果的在线协作编辑
- 实时协同分析功能

### 1.3 术语定义
| 术语 | 定义 |
|------|------|
| 文件分析 | 使用 AI 对文件内容进行智能分析，输出数据概览、关键发现、问题诊断和优化建议 |
| 批量分析 | 一次选择多个文件，依次或并行对每个文件执行 AI 分析 |
| 分析报告 | 将一个或多个文件的分析结果整合，导出为结构化文档（Markdown/PDF） |
| 结构化存储 | 将 AI 分析结果以结构化格式（JSON）持久化保存，便于后续查询和导出 |
| 文件内容提取器 | 针对不同文件格式的解析组件，负责将二进制/结构化文件转换为可分析的文本内容 |

## 2. 需求

### 2.1 功能需求

#### REQ-01: PDF 文件内容提取
- **描述**: 系统应支持从 PDF 文件中提取文本内容，使 PDF 文件能够被 AI 分析，而非仅返回二进制文件大小信息
- **优先级**: 高
- **EARS格式**: The 文件分析系统 shall 支持从 PDF 文件中提取文本内容用于 AI 分析
- **验收标准**:
  - AC-01-1: 当用户请求读取 .pdf 文件内容时，系统应返回提取的文本内容而非"二进制文件"占位信息
  - AC-01-2: 当用户对 .pdf 文件发起 AI 分析时，系统应将提取的 PDF 文本内容作为 prompt 发送给 AI
  - AC-01-3: 对于包含多页的 PDF 文件，系统应提取所有页面的文本内容
  - AC-01-4: 若 PDF 文件为扫描件（纯图片无文本层），系统应返回提示信息说明该文件无法提取文本

#### REQ-02: Excel 文件内容解析
- **描述**: 系统应支持解析 Excel 文件（.xlsx/.xls），提取工作表名称、列头、数据行等信息，使 Excel 文件能够被 AI 分析
- **优先级**: 高
- **EARS格式**: The 文件分析系统 shall 支持解析 Excel 文件并提取工作表结构与数据内容
- **验收标准**:
  - AC-02-1: 当用户请求读取 .xlsx 或 .xls 文件内容时，系统应返回解析后的结构化数据（包含工作表名称、列头、数据行）
  - AC-02-2: 当用户对 Excel 文件发起 AI 分析时，系统应将解析后的数据内容作为 prompt 发送给 AI
  - AC-02-3: 对于包含多个工作表的 Excel 文件，系统应提取所有工作表的数据
  - AC-02-4: 提取的 Excel 数据应包含基本统计信息（行数、列数、数值列的统计摘要）

#### REQ-03: Word 文件内容解析
- **描述**: 系统应支持解析 Word 文档（.docx），提取文档的文本内容（包括段落、标题、表格），使 Word 文件能够被 AI 分析
- **优先级**: 高
- **EARS格式**: The 文件分析系统 shall 支持解析 Word 文档并提取文本内容
- **验收标准**:
  - AC-03-1: 当用户请求读取 .docx 文件内容时，系统应返回提取的文本内容
  - AC-03-2: 当用户对 .docx 文件发起 AI 分析时，系统应将提取的文本内容作为 prompt 发送给 AI
  - AC-03-3: Word 文档中的表格内容应被提取并以结构化文本形式呈现
  - AC-03-4: Word 文档的标题层级结构应在提取内容中保留

#### REQ-04: 文件格式分类扩展
- **描述**: 系统的文件列表接口应扩展文件格式分类，新增对 Excel、Word 等格式的类别标识
- **优先级**: 中
- **EARS格式**: The 文件分析系统 shall 在文件列表中对新增支持的文件格式（Excel、Word）提供正确的类别标识
- **验收标准**:
  - AC-04-1: .xlsx 和 .xls 文件在文件列表中的 category 应为 "excel"
  - AC-04-2: .docx 文件在文件列表中的 category 应为 "word"
  - AC-04-3: .pdf 文件在文件列表中的 category 应保持为 "pdf"，但其内容读取行为应从"二进制"变为"文本提取"

#### REQ-05: 批量文件分析
- **描述**: 系统应支持用户一次选择多个文件，对所选文件依次执行 AI 分析，并返回每个文件的分析结果
- **优先级**: 高
- **EARS格式**: When 用户选择多个文件并触发批量分析, the 文件分析系统 shall 对所有选中文件依次执行 AI 分析并返回各文件的分析结果
- **验收标准**:
  - AC-05-1: 用户可通过 API 传入多个文件路径，系统对每个文件执行 AI 分析
  - AC-05-2: 批量分析结果应包含每个文件的分析输出，并标识对应文件名
  - AC-05-3: 若某个文件分析失败，系统应记录该文件的错误信息，并继续分析其余文件
  - AC-05-4: 批量分析应支持选择 AI 模型提供者（provider）和会话标识（sessionId）
  - AC-05-5: 单次批量分析的文件数量上限为 20 个

#### REQ-06: 批量分析进度跟踪
- **描述**: 在批量分析执行过程中，系统应提供进度信息，包括已完成数量、总数量和当前正在分析的文件
- **优先级**: 中
- **EARS格式**: While 批量分析正在进行, the 文件分析系统 shall 提供实时进度信息（已完成数/总数、当前文件）
- **验收标准**:
  - AC-06-1: 批量分析过程中，客户端可通过进度查询接口获取当前进度（已完成数、总数、当前文件名）
  - AC-06-2: 批量分析完成后，进度信息应标记为完成状态
  - AC-06-3: 批量分析失败时，进度信息应标记为失败状态并包含错误描述

#### REQ-07: 分析结果结构化存储
- **描述**: 系统应将 AI 分析结果以结构化格式持久化存储，便于后续查询和导出
- **优先级**: 高
- **EARS格式**: When AI 完成对文件的分析, the 文件分析系统 shall 将分析结果以结构化格式持久化存储
- **验收标准**:
  - AC-07-1: 每次分析完成后，系统应将分析结果保存，包含文件路径、分析时间、AI 模型、分析内容
  - AC-07-2: 用户可通过 API 查询指定文件的历史分析结果列表
  - AC-07-3: 用户可通过 API 查询所有文件的分析结果列表（支持分页）
  - AC-07-4: 分析结果存储应支持覆盖或追加模式

#### REQ-08: 分析结果导出为 Markdown 报告
- **描述**: 系统应支持将一个或多个文件的分析结果导出为 Markdown 格式的报告文件
- **优先级**: 高
- **EARS格式**: When 用户请求导出分析结果为 Markdown, the 文件分析系统 shall 生成包含分析结果的 Markdown 格式报告
- **验收标准**:
  - AC-08-1: 用户可选择一个或多个文件的分析结果，导出为单个 Markdown 文件
  - AC-08-2: 导出的 Markdown 报告应包含报告标题、生成时间、各文件的分析内容（含文件名、分析时间、AI 模型、分析结果）
  - AC-08-3: 多文件导出时，每个文件的分析结果应作为独立章节呈现
  - AC-08-4: 导出的 Markdown 文件应使用 UTF-8 编码

#### REQ-09: 分析结果导出为 PDF 报告
- **描述**: 系统应支持将一个或多个文件的分析结果导出为 PDF 格式的报告文件
- **优先级**: 中
- **EARS格式**: When 用户请求导出分析结果为 PDF, the 文件分析系统 shall 生成包含分析结果的 PDF 格式报告
- **验收标准**:
  - AC-09-1: 用户可选择一个或多个文件的分析结果，导出为单个 PDF 文件
  - AC-09-2: 导出的 PDF 报告应包含报告标题、生成时间、各文件的分析内容
  - AC-09-3: PDF 报告应支持中文字符正确渲染
  - AC-09-4: 若 PDF 生成失败，系统应返回明确的错误信息

#### REQ-10: 文件内容提取大小限制
- **描述**: 对于新增的文件格式（PDF、Excel、Word），系统应对提取的内容设置合理的大小限制，防止内存溢出
- **优先级**: 中
- **EARS格式**: If 提取的文件内容超过大小限制, then the 文件分析系统 shall 截断内容并附加截断提示信息
- **验收标准**:
  - AC-10-1: PDF 提取文本内容超过 500KB 时应截断并附加截断提示
  - AC-10-2: Excel 解析数据超过 500KB 时应截断并附加截断提示
  - AC-10-3: Word 提取文本内容超过 500KB 时应截断并附加截断提示
  - AC-10-4: 发送给 AI 的内容超过 100KB 时应截断并附加截断提示

### 2.2 非功能需求

#### NFR-01: 文件解析性能
- **描述**: 文件内容提取操作应在合理时间内完成，不阻塞主线程
- **验收标准**:
  - AC-NFR-01-1: 单个 10MB 以内的 PDF 文件文本提取应在 5 秒内完成
  - AC-NFR-01-2: 单个 5MB 以内的 Excel 文件解析应在 3 秒内完成
  - AC-NFR-01-3: 单个 5MB 以内的 Word 文件解析应在 3 秒内完成

#### NFR-02: 文件解析容错性
- **描述**: 文件解析组件应具备容错能力，对损坏或非标准格式的文件提供友好的错误处理
- **验收标准**:
  - AC-NFR-02-1: 若 PDF 文件损坏无法解析，系统应返回明确的错误信息而非抛出未捕获异常
  - AC-NFR-02-2: 若 Excel 文件损坏无法解析，系统应返回明确的错误信息而非抛出未捕获异常
  - AC-NFR-02-3: 若 Word 文件损坏无法解析，系统应返回明确的错误信息而非抛出未捕获异常
  - AC-NFR-02-4: 加密/受密码保护的文件应返回"文件受保护，无法解析"的提示信息

#### NFR-03: API 兼容性
- **描述**: 新增功能应以新增 API 端点为主，现有 API 的行为变更应保持向后兼容
- **验收标准**:
  - AC-NFR-03-1: 现有的单文件分析接口（/api/files/analyze）应保持原有行为不变
  - AC-NFR-03-2: 现有的文件内容读取接口（/api/files/content）对 PDF 文件的行为变更为返回提取文本，但响应结构保持一致
  - AC-NFR-03-3: 新增的批量分析、结果存储、导出等接口应使用新的 API 路径

#### NFR-04: 报告导出质量
- **描述**: 导出的报告应具有良好的排版和可读性
- **验收标准**:
  - AC-NFR-04-1: Markdown 报告应使用标准 Markdown 语法，可在常见渲染器中正确显示
  - AC-NFR-04-2: PDF 报告应具有清晰的标题层级、合理的页边距和字体大小

## 3. 约束与假设
### 3.1 约束
- 项目基于 Spring Boot 3.3.2 + Spring AI 1.0.0-M1，Java 22
- 文件解析库需通过 Maven 依赖引入，优先选择成熟的开源库
- AI 分析仍基于现有的 ChatService 流式对话机制
- 分析结果存储使用本地文件系统（JSON 格式），不引入数据库
- PDF 报告生成需依赖外部库，需考虑跨平台兼容性
- 单次批量分析文件数上限为 20

### 3.2 假设
- 待分析的 PDF 文件主要为文本型 PDF（非纯扫描件）
- Excel 文件数据量在常规范围内（单表不超过 10 万行）
- Word 文档以 .docx 格式为主，.doc（旧格式）为可选支持
- 用户有足够的磁盘空间存储分析结果和导出报告
- AI 模型对提取的文件内容有足够的上下文窗口处理能力

## 4. 依赖关系
- Apache PDFBox（PDF 文本提取）
- Apache POI（Excel 和 Word 文件解析）
- iText 或 OpenPDF（PDF 报告生成）
- 现有 ChatService（AI 流式对话服务）
- 现有 FileController 路径安全校验机制（safePath）
